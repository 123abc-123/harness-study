# 从问答系统到可操作文件的 Agent：原理、复用方案与 KG 原型

> 本文保留为第一版方案记录。公司不能使用厂商 SDK/API 的最新路线，以及更详细的机制与难点分析，请阅读 [V2 详细技术报告](../harness_v2/docs/REPORT.zh-CN.md)。

日期：2026-11-01。对象：Python 框架；按章节嵌套的 JEDEC 知识图谱 JSON；输入规模预计为数百 MB。

## 结论与项目目标

主流 coding agent 能读写文件，是因为产品把模型接到了文件工具、执行进程、权限策略和多轮执行循环。文件访问不是大模型天然拥有的能力，也不是 coding 模型独占的能力。普通问答或 RAG 系统通常只实现“检索后回答”，没有配置文件操作工具及其执行权限，因此不会直接修改业务文件。

RAG 与文件操作并不冲突。RAG 可以成为 agent 的证据获取工具；agent harness 则负责让模型调用工具、观察结果、继续执行并交付产物。项目应先建设可读写文件的运行底座，再将 JEDEC 查询与比较作为领域工具接入。

本次交付包括一个最小 Python harness、真实 Deep Agents 复用入口、虚构 KG 样例、离线演示及自动化测试。这是可检查、可扩展的原型，不是对任一商业 coding agent 的完整复刻。

## 一、为什么 coding agent 能读写文件

### 1. 模型、工具与权限分别负责什么

| 组成 | 职责 | 缺失时的表现 |
| --- | --- | --- |
| 模型 | 根据任务和上下文提出工具调用 | 无法动态决定下一步 |
| 工具协议 | 描述工具名、参数和返回结构 | 模型不知道如何请求操作 |
| 工具执行器 | 将调用映射到真实文件/API/进程操作 | 只会生成“应该怎么操作”的文字 |
| 运行环境 | 提供磁盘、进程及操作系统权限 | 只能访问远端环境，或执行被拒绝 |
| Harness | 循环调用、保存状态、处理错误、限制预算 | 一次调用后无法继续完成任务 |
| 验证器 | 检查文件、格式、差异和业务结果 | 容易“说已完成”但产物无效 |

函数调用是一个交互协议：模型提出调用，应用负责执行并返回结果。仅把 `write_file` 写进提示词不会赋予磁盘访问能力。OpenAI 的官方函数调用文档说明了这种模型与应用分工。[官方说明](https://developers.openai.com/api/docs/guides/function-calling)

### 2. 三种系统的典型执行路径

```text
普通问答：用户 → 模型 → 文本
传统 RAG：用户 → 检索 → 模型结合证据 → 文本
可执行 agent：用户 → 模型 → 权限检查 → 工具执行 → 结果 → 模型 → … → 产物
```

以上是典型部署方式，并非技术上的互斥分类。问答应用接入文件工具后同样能保存报告。固定步骤的报告生成可以使用普通工作流，不必为了写文件引入自主 agent。需要根据检索结果、执行错误和文件内容决定后续操作时，agent 循环才更有价值。

### 3. “有工具”不等于“有权限”

模型可能请求修改某文件，但是否执行由工具层和操作系统决定。云端工具能写云端沙箱，不代表能写用户电脑。还要区分可读目录、可写目录、网络权限、进程权限和用户审批策略。

路径检查可约束显式文件工具，但约束不了任意 Python/shell 程序。`cwd=workspace` 只是指定起始目录，并非沙箱。开启程序执行后，应使用受限容器或操作系统隔离；宿主机进程继承的权限不能靠提示词收回。

## 二、如何复用现有主流 harness

优先复用稳定的 SDK、工具接口和后端抽象，而不是复制 UI、提示词或整套仓库。对依赖采用锁定版本并跑回归测试；源码复制另需检查许可证与维护成本。

| 方案 | 可复用内容 | 如何接入本项目 | 主要考虑 |
| --- | --- | --- | --- |
| Claude Agent SDK | Claude Code 的工具、循环、上下文管理、权限与会话 | Python 应用调用 SDK，用自定义工具/MCP 接 KG | 模型生态、认证、部署与数据策略 |
| Codex SDK / app-server | 现有 Codex 执行环境、会话与事件 | 应用启动/续接任务，通过工具或程序访问 KG | 需要管理 Codex runtime、账户与环境权限 |
| Deep Agents | 多步执行、上下文管理、文件后端和工具扩展 | Python 中把现有 KG 和文件工具传给 `create_deep_agent` | 后端选择、依赖版本、实际文件与虚拟文件的区别 |
| 最小自建循环 | 完全可检查的协议、工具注册、错误反馈和记录 | 作为当前框架的基线及测试载体 | 生产级恢复、压缩、并发需要继续建设 |

Claude 官方提供 Python/TypeScript Agent SDK，并明确支持文件读写、命令执行和自定义工具。[Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview)

Codex 官方 SDK 页面提供 TypeScript 和 Python 接入说明；Python SDK 通过 JSON-RPC 控制本地 app-server。SDK 是调用现有 runtime 的入口，不会自动赋予所有系统权限。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)

Deep Agents 可以配置模型、领域工具及文件后端；StateBackend 中的文件属于状态存储，FilesystemBackend 才对应实际文件系统，执行命令还需要相应后端支持。[自定义配置](https://docs.langchain.com/oss/python/deepagents/customization)、[后端说明](https://docs.langchain.com/oss/python/deepagents/backends)

### 本项目的选择

采用“统一领域工具 + 可替换执行循环”：

1. `Runtime` 是唯一工具注册入口，承载文件操作、KG 查询和版本比较。
2. `Agent` 是透明的基线循环，用来观察主流 harness 的核心机制，也可对接支持工具调用的模型。
3. `deepagents_backend.py` 是实际复用入口：由 Deep Agents 接管模型/工具循环，业务工具不变。
4. Deep Agents 的内置文件系统用于内部状态；真实工作区操作通过 `kg_` 前缀工具。当前未附加可能绕开本项目文件策略的宿主机文件或 shell 后端。

没有把多个主流 harness 同时嵌入同一次任务，也没有声称自建循环等同于完整 Claude Code 或 Codex。Claude/Codex 的接入在本次是设计说明，Deep Agents 则交付可选适配代码。

## 三、第一版已实现的能力

### 通用运行底座

- 列目录、分段读取 UTF-8 文件、字面搜索。
- 新建文件、基于 SHA-256 的覆盖检查、精确一次文本替换。
- 显式工具注册和参数类型检查；未知工具与禁用工具不可调用。
- 模型 → 工具 → 观察结果的循环；错误回传模型；模型决定是否修正。
- 顺序执行工具，限制步数和单轮调用数；上下文超限时明确停止。
- 大工具结果保存到文件，给模型返回位置与摘要。
- 保存消息状态和工具执行前后事件；尚未实现进程崩溃后的自动续跑及 exactly-once 执行。
- 命令执行支持禁用、Docker、显式信任的本机执行三种模式；默认禁用。

文件工具限制在工作区；输入只读，`work/` 与 `outputs/` 可写。拒绝路径穿越、隐藏状态路径、符号链接及可识别的 Windows junction。该策略针对单用户原型，不是抵御恶意并发文件替换的 OS 安全边界。

Docker 配置不开放网络，不挂载宿主凭据，输入挂载只读，只给工作目录和输出目录写权限，并设置内存、进程数、CPU 和超时限制。容器仍需要运维配置、可写挂载权限和真实环境验证；这里不把“配置了参数”写成“已经验证隔离安全”。本机模式不提供系统隔离，仅用于可信开发任务。

### KG 功能

输入使用章节嵌套 JSON，自定义 `schema_version=1`，节点/关系保留在章节中。`NestedJSONAdapter` 负责格式转换，工具和 agent 不依赖原始 JSON 字段路径。

导入后使用 SQLite 保存版本、章节、实体、关系及证据定位，并建立 FTS5 全文索引。未安装 `ijson` 时，超过 32 MB 的输入明确拒绝；安装后按顶层章节读取，峰值内存仍取决于最大的单个顶层章节。尚未对用户的几百 MB 真实图谱做性能验收。

问答有两条路径：离线命令返回关键词证据与来源；真实模型模式可多轮查询后生成带依据的答案。离线检索不冒充语义理解或完整问答，中文自然语言检索效果仍需迭代。

版本比较遍历导入记录，以跨版本稳定 `stable_key` 对齐，报告新增、删除和修改；输出完整 JSON 和 Markdown。条款编号变化不会导致有相同 stable_key 的记录被误报为新增/删除。忽略仅 `source` 元数据变化造成的内容差异，但在输出的两侧证据中保留来源。

## 四、必须明确的适用边界

1. 当前比较是图谱记录级差异，不是经原始 JEDEC 文档核验的修订解释。解析器/图算法变化也可能产生差异。
2. `stable_key` 的跨版本稳定性是数据契约。真实文件若不存在可靠标识，需要另做匹配、拆分合并和人工复核；不能把章节编号直接当成永久标识。
3. 还没有单位换算、数值容差、语义等价和适用条件推理。数值/文本变化按记录原值比较。
4. 关系中的 `origin` 应区分原文抽取与算法推导；图上连通不能直接当作规范要求或因果关系。
5. 一个工作区当前用于一个标准系列；版本标签在工作区内唯一。多个标准用不同工作区，后续可扩展复合键。
6. 搜索未命中不等于不存在规定；检索与摘要不能证明全量差异覆盖。
7. 对外模型调用会发送任务与选中的工具结果，部署前需按组织数据政策配置模型服务；本次未自动上传真实 JEDEC 文件。

## 五、后续推进顺序与验收

先用当前脚本验证文件读写、修改与程序执行；配置选定模型后验证模型能自主调用这些工具。然后拿真实 JSON 调整适配器，以人工标注的问答和版本差异检查正确性。生产化时再补并发任务隔离、幂等恢复、锁定依赖、权限审批、成本预算和业务验证器。

验收应分别记录：工具层成功率、真实模型任务完成率、证据准确率、差异召回/误报、失败恢复、输入大小及内存耗时。脚本化演示通过只能证明执行链路，不证明模型推理质量。当前验证记录见 `VALIDATION.md`。
